Scrutinize Report: Dashboard Feature & Layouts Module

วันที่: 14 กรกฎาคม 2569 | ตรวจสอบ: src/app/features/dashboard + src/app/layouts

1. เจตนา (Intent)

เป้าหมาย: ตรวจสอบว่า Dashboard feature module (domain/data/presentation) และ Layouts module ทำงานเชื่อมต่อกัน end-to-end ได้จริง — คือ user คลิก dashboard แล้วเห็นข้อมูลจริงจาก API ผ่าน use case chain

มีวิธีง่ายกว่าไหม? ปัญหาไม่ใช่เรื่อง approach — โค้ดเขียนไว้แล้ว ปัญหาคือ ชั้นโค้ดเชื่อมกันไม่ได้เลย ดังนั้นสิ่งที่มีค่ากว่าคือไล่ให้เห็นว่าจุดไหนขาดตรงไหน

2. ติดตาม — เดิน code path จริง

3. ตรวจสอบ — ทำได้จริงตามที่อ้างไหม

Claim: "Clean Architecture 3 ชั้นทำงานได้"
ไม่จริง. Domain/Data layer ถูกสร้างไว้สมบูรณ์ แต่ Presentation layer ไม่ได้ inject หรือเรียก Use Case ใดๆ ทั้ง 3 components ใช้ hard-coded mock data ชั้นทั้ง 3 แยกจากกันโดยสิ้นเชิง
Claim: "DI Token pattern ทำให้ swappable"
ไม่จริง. Token + Provider + Use Case injection infrastructure ถูกต้อง แต่ไม่มี component ไหนเข้าถึง chain นี้ ทำให้ไม่สามารถ test หรือ swap ได้จริง
Claim: "Dashboard แสดงข้อมูลจาก API"
ไม่จริง. MainDashboardComponent ใช้ setTimeout(1000ms) + hard-coded values ไม่มี HTTP call เกิดขึ้น
Claim: "Reports page ใช้งานได้"
ไม่จริง. ไม่มี route registration → user คลิกแล้วเจอ 404
Claim: "Tests ครอบคลุม"
ไม่จริง. ทุก spec ทดสอบแค่ "component should create" — ไม่มี test ที่ inject use case, mock API, หรือ verify data flow

4. Findings

BLOCKER #1: ReportsComponent ไม่มี route — ไม่สามารถเข้าถึงได้
สิ่งที่เจอ: ไม่มี route entry สำหรับ /reports ใน app-routing.module.ts:67-227 แต่มี 3 จุดที่ link ไปที่ /reports
ทำไมถึงสำคัญ: User คลิก "Reports" จาก sidebar หรือ header → Angular Router หา route ไม่เจอ → แสดง blank page หรือ error — feature ใช้งานไม่ได้
หลักฐาน:
app-routing.module.ts:71-226 — children ของ AppLayoutComponent: path: 'dashboard' ✓ (line 73) path: 'analytics' ✓ (line 157) path: 'reports' ❌ ไม่มี! Link ที่ชี้ไป /reports (3 จุด): sidebar.component.ts menuItems: { route: '/reports' } header.component.ts horizontalMenu: { route: '/reports' } header.component.ts app dropdown: <a href="/reports">
แนวทางแก้ไข:
  • เพิ่ม route ใน app-routing.module.ts หลัง line 162:
  • { path: 'reports', loadComponent: () => import('./features/dashboard/presentation/pages/reports/reports.component').then((m) => m.ReportsComponent) },
BLOCKER #2: Presentation layer ไม่ได้เชื่อมกับ Domain/Data layer — ทั้ง Use Case chain เป็น dead code
สิ่งที่เจอ: ทั้ง 3 components ไม่มีตัวไหน inject หรือ import Use Case จาก domain layer
ทำไมถึงสำคัญ: Domain layer (3 use cases), Data layer (repository impl, datasource, DTO) ทั้งหมดถูกสร้างไว้สมบูรณ์แต่ไม่เคยถูกเรียกใช้ — เป็น dead code ที่เพิ่ม complexity โดยไม่ได้ value
หลักฐาน:
main-dashboard.component.ts imports: Component, OnInit, CommonModule, BehaviorSubject, TranslatePipe → ❌ ไม่มี GetDashboardStatsUseCase → ❌ ไม่มี GetRevenueChartUseCase reports.component.ts imports: Component, CommonModule, RouterLink, TranslatePipe → ❌ ไม่มี GenerateReportUseCase analytics.component.ts imports: Component, CommonModule, TranslatePipe → ❌ ไม่มี Use Case ใดๆ DashboardApiDataSource ทั้งไฟล์: → ไม่มีใคร inject → ไม่มี HTTP request เกิดขึ้นจริง
แนวทางแก้ไข:
  • Inject GetDashboardStatsUseCase และ GetRevenueChartUseCase ใน MainDashboardComponent
  • เรียก execute() ใน ngOnInit() แล้ว subscribe ลง statsSubject
  • ลบ setTimeout mock data ออก
  • ทำเช่นเดียวกันกับ ReportsComponent (inject GenerateReportUseCase) และ AnalyticsComponent
MAJOR #1: MainDashboardComponent นิยาม DashboardStats interface ซ้ำ — field name ไม่ตรงกัน
สิ่งที่เจอ: main-dashboard.component.ts:7-12 นิยาม local DashboardStats interface ที่มี field revenue แต่ domain entity (dashboard-stats.entity.ts:3) ใช้ totalRevenue + monthlyRevenue
ทำไมถึงสำคัญ: ถ้าเชื่อมกับ use case จริง → domain entity คืน { totalRevenue: 45230 } → template แสดง s.revenue → undefined → แสดง "THB0"
หลักฐาน:
main-dashboard.component.ts:7-12 (local): interface DashboardStats { ..., revenue: number, ... } dashboard-stats.entity.ts:3 (domain): export interface DashboardStats { ..., totalRevenue: number, monthlyRevenue: number, ... } main-dashboard.component.html:34: {{ s.revenue | currency:'THB':'symbol':'1.0-0' }} ← field นี้ไม่มีใน domain entity!
แนวทางแก้ไข: ลบ local interface ออก แล้ว import จาก domain entity แล้วแก้ template เป็น {{ s.totalRevenue | currency:'THB':'symbol':'1.0-0' }}
MAJOR #2: ReportsComponent download button ไม่มี click handler
สิ่งที่เจอ: reports.component.html มีปุ่ม download แต่ไม่มี (click) binding — คลิกแล้วไม่ทำอะไร
ทำไมถึงสำคัญ: ปุ่ม download เป็น UI element หลักของหน้า reports แต่ไม่มี functionality
หลักฐาน:
<button class="btn btn-sm btn-primary"> {{ 'reports.download' | translate }} </button> <!-- ไม่มี (click)="download(r)" หรือ event binding ใดๆ -->
แนวทางแก้ไข: เพิ่ม click handler ที่เรียก GenerateReportUseCase.execute() แล้ว download blob ที่ได้
MAJOR #3: HeaderComponent.logout() ลบ localStorage ทั้งหมด — สูญเสีย theme settings
สิ่งที่เจอ: header.component.ts logout() เรียก localStorage.clear() ซึ่งลบ theme/font/radius ที่ LayoutService เก็บไว้ด้วย
ทำไมถึงสำคัญ: User login ใหม่แล้วจะต้องตั้ง theme ใหม่ทุกครั้ง เพราะข้อมูล settings หายไป
หลักฐาน:
header.component.ts: logout(): localStorage.clear() ← ลบ key ทั้งหมดรวมถึง 'theme', 'theme-primary' ฯลฯ layout.service.ts ใช้ localStorage สำหรับ: 'theme', 'theme-base', 'theme-font', 'theme-primary', 'theme-radius'
แนวทางแก้ไข: ลบเฉพาะ auth-related keys แทน เช่น localStorage.removeItem('token')
MAJOR #4: สอง translate pipe ต่างกัน — ใช้สลับกันใน layout
สิ่งที่เจอ: Layouts ใช้ translate pipe 2 ตัวที่ต่างกัน — LayoutSettingsComponent ใช้ AppTranslatePipe (custom I18nService) ส่วน component อื่นใช้ TranslatePipe (@ngx-translate)
ทำไมถึงสำคัญ: ถ้า I18nService และ TranslateService มี translation data ต่างกัน → LayoutSettings แสดงข้อความภาษาหนึ่ง แต่ส่วนอื่นแสดงอีกภาษา
หลักฐาน:
layout-settings.component.ts:5: import { AppTranslatePipe } from '.../i18n/presentation/pipes/translate.pipe' → uses I18nService.translate() header/sidebar/footer: import { TranslatePipe } from '.../shared/pipes/translate.pipe' → uses TranslateService.instant() TranslatePipe (shared/pipes): → inject TranslateService from @ngx-translate/core → subscribes to onLangChange, handles cleanup AppTranslatePipe (shared/i18n): → inject I18nService (custom) → no subscription, no cleanup
แนวทางแก้ไข: เลือกใช้ pipe ตัวใดตัวหนึ่งให้ทั้ง project — แนะนำ TranslatePipe (@ngx-translate) ตัวเดียว
MAJOR #5: Navigation ซ้ำกันระหว่าง sidebar และ header — ต้อง sync มือ
สิ่งที่เจอ: Sidebar และ Header ต่างมี menu items list ของตัวเองที่ overlap กัน แต่ไม่มี single source of truth
ทำไมถึงสำคัญ: เพิ่ม menu ใหม่ ต้องแก้ 2 ที่ ถ้าแก้ที่เดียวจะไม่ sync → user เห็น menu ต่างกัน
หลักฐาน:
sidebar.component.ts menuItems: [ { label: 'nav.dashboard', route: '/dashboard' }, { label: 'nav.jobs', route: '/jobs', children: [3 items] }, { label: 'nav.reports', route: '/reports' }, ... (13 items) ] header.component.ts horizontalMenu: [ { label: 'Dashboard', route: '/dashboard' }, { label: 'Jobs', route: '/jobs', children: [2 items] }, { label: 'Reports', route: '/reports' }, ] → label ต่างกัน ('nav.dashboard' vs 'Dashboard') → children ต่างกัน (sidebar มี 3, header มี 2)
แนวทางแก้ไข: สร้าง shared NavigationConfig service หรือ constant ที่ทั้ง 2 import ใช้ร่วมกัน
NIT #1: DashboardStatsResponseDto ไม่ได้ใช้งาน
สิ่งที่เจอ: data/dtos/dashboard-stats-response.dto.ts นิยามไว้แต่ไม่มีไฟล์ไหน import
แนวทางแก้ไข: ใช้ใน DashboardApiDataSource.getStats() return type แทน Observable<any>
NIT #2: DashboardApiDataSource ใช้ Observable<any> ทุก method
สิ่งที่เจอ: dashboard.api.datasource.ts return Observable<any> ทุก method — ไม่มี type safety
แนวทางแก้ไข: ใช้ DashboardStatsResponseDto เป็น return type
NIT #3: MainDashboardComponent setTimeout ไม่ cleanup
สิ่งที่เจอ: main-dashboard.component.ts ใช้ setTimeout(1000ms) แต่ไม่ clear ใน ngOnDestroy
แนวทางแก้ไข: เก็บ timeout id แล้ว clear ใน ngOnDestroy หรือใช้ takeUntil pattern
NIT #4: Tests ไม่ cover data flow
สิ่งที่เจอ: ทุก spec ทดสอบแค่ "component should create" — ไม่มี test ที่ inject mock use case แล้ว verify data flow
แนวทางแก้ไข: เพิ่ม tests ที่ inject mock use case แล้ว verify ว่า execute() ถูกเรียก

Verdict

REWORK
เหตุผลใหญ่สุด: Dashboard feature มี architecture ที่ออกแบบไว้ดี (Clean Architecture + DI Token) แต่ presentation layer ไม่ได้เชื่อมกับ domain/data layer เลย ทำให้ทั้ง Use Case chain เป็น dead code + ReportsComponent ไม่มี route (เข้าถึงไม่ได้) + template ใช้ field name ผิด (revenue vs totalRevenue) → จะพังทันทีถ้าเชื่อมจริง
