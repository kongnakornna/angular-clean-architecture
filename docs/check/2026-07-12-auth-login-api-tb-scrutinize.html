Scrutinize Report: Auth Login API

วันที่: 12 กรกฎาคม 2569 | ตรวจสอบ: http://localhost:5000/api/auth/login

1. เจตนา (Intent)

เป้าหมาย: เรียก API http://localhost:5000/api/auth/login เพื่อเข้าสู่ระบบ และตรวจสอบว่า API อื่นๆ สามารถเรียกใช้งานได้หรือไม่

มีวิธีง่ายกว่าไหม? ไม่ — ปัญหาไม่ใช่เรื่องวิธีทำ แต่เป็นเรื่อง configuration mismatch ระหว่าง frontend กับ backend

2. Code Path ที่ตรวจสอบ

LoginComponent ↓ LoginUseCase.execute() ↓ AuthRepositoryImpl.login() ↓ AuthApiDataSource.login() ↓ POST ${apiBaseUrl}/auth/login ↓ = http://localhost:5000/api/auth/login

3. Findings

BLOCKER #1: Backend ไม่ได้รันอยู่
สิ่งที่เจอ: Backend server ที่ port 5000 ไม่ได้รันอยู่ ทำให้ทุก API call fail ทั้งหมด
ทำไมถึงสำคัญ: ถ้า server ไม่รัน ไม่ว่าจะแก้โค้ดอย่างไรก็เรียก API ไม่ได้
หลักฐาน: ไม่สามารถ verify จากโค้ดได้ ต้องตรวจสอบ server จริง
แนวทางแก้ไข:
  • รัน backend server ที่ port 5000
  • ทดสอบด้วย curl http://localhost:5000/ping หรือ http://localhost:5000/health
BLOCKER #2: Path Mismatch ระหว่าง Frontend/Backend
สิ่งที่เจอ: Frontend เรียก /api/auth/login แต่ backend อาจตั้ง path ไว้เป็น /auth/login (ไม่มี /api prefix)
ทำไมถึงสำคัญ: Path ไม่ตรงกัน → 404 Not Found ทุกครั้ง
หลักฐาน:
app.config.ts:49 → apiBaseUrl = 'http://localhost:5000/api' api.config.ts:3 → login: '/auth/login' Result → http://localhost:5000/api/auth/login ถ้า backend route = '/auth/login' → ไม่ตรงกัน!
แนวทางแก้ไข:
  • ตรวจสอบ backend ว่า route จริงคืออะไร
  • ถ้า backend ใช้ /auth/login ให้แก้ api.config.ts เป็น login: '/login'
  • หรือแก้ app.config.ts:49 เป็น apiBaseUrl: environment.useProxy ? '/api' : environment.apiTargetUrl (ลบ /api ออก)
MAJOR #1: Token Storage ซ้ำซ้อน
สิ่งที่เจอ: ทั้ง AuthRepositoryImpl.login() และ LoginUseCase.execute() ต่างเก็บ token ลง localStorage ทำให้เก็บซ้ำกัน 2 ครั้ง
ทำไมถึงสำคัญ: Dead code ที่ทำให้สับสน และอาจสร้างปัญหาถ้ามี logic ที่ต้องพึ่งพา "การ set ครั้งแรก"
หลักฐาน:
auth.repository.impl.ts:18-19: localStorage.setItem(TOKEN_KEY, dto.accessToken); localStorage.setItem(REFRESH_TOKEN_KEY, dto.refreshToken); login.use-case.ts:16-20: localStorage.setItem(TOKEN_KEY, response.accessToken); localStorage.setItem(REFRESH_TOKEN_KEY, response.refreshToken); localStorage.setItem(EXPIRES_IN_KEY, ...); localStorage.setItem(TOKEN_TYPE_KEY, ...); localStorage.setItem(USER_KEY, ...);
แนวทางแก้ไข: เลือกที่เดียว — แนะนำให้เก็บใน LoginUseCase เพราะมี logic เพิ่มเติม (expiresIn, tokenType, user) และลบออกจาก AuthRepositoryImpl
MAJOR #2: User Permissions ว่างเปล่าเสมอ
สิ่งที่เจอ: AuthRepositoryImpl.mapToUser() hardcode permissions: [] เสมอ ไม่เคยดึง permissions จริงมาใส่
ทำไมถึงสำคัญ: PermissionGuard ที่เช็ค job_card.view จะไม่ทำงานถูกต้อง เพราะ permissions ว่างเสมอ → user ทุกคนจะ access ไม่ได้
หลักฐาน:
auth.repository.impl.ts:175: permissions: [], // ไม่เคยดึง permissions จริงมาใส่
แนวทางแก้ไข: เรียก getPermissions() หลัง login สำเร็จ แล้วใส่ permissions ลงใน User entity
NIT #1: Root Level Variants ไม่ได้ใช้งาน
สิ่งที่เจอ: api.config.ts:16-17 กำหนด loginRoot: '/login' และ signinRoot: '/signin' แต่ไม่มีโค้ดไหนเรียกใช้
ทำไมถึงสำคัญ: Dead code ที่อาจทำให้สับสน
แนวทางแก้ไข: ลบออก หรือใช้งานให้ถูกต้อง

4. Verdict

REWORK
เหตุผลใหญ่สุด: ปัญหาเชิง configuration ทำให้ไม่สามารถเรียก API ได้เลย ต้องแก้ให้ path ตรงกันก่อน แล้วค่อยแก้เรื่อง permissions ที่ไม่ทำงาน

5. แผนการแก้ไข (Recommended Order)

  1. ตรวจสอบ backend server — รันอยู่ที่ port 5000 หรือไม่
  2. ตรวจสอบ backend route — /auth/login หรือ /api/auth/login
  3. แก้ path ให้ตรง — แก้ api.config.ts หรือ app.config.ts
  4. ลบ token storage ซ้ำ — เลือกที่เดียว
  5. เพิ่ม permissions fetch — หลัง login สำเร็จ
  6. ลบ root level variants — cleanup dead code
